# Release v1.0.9 — SonarQube Cleanup, Hardware-Validated

**ASUS ZenBook Linux Tools v1.0.9** clears the 1,795 maintainability findings
SonarQube Cloud raised against the shell code base, without changing behaviour,
and fixes the defects found while validating that cleanup on a real ZenBook
Pro Duo (UX582HS), including Esc on the Display Toggle OSD applying the layout.

---

## 🌟 Key Features & Improvements

### 🧹 SonarQube shell cleanup (behaviour-preserving)

- **`[[ … ]]` everywhere** in product, installer, packaging and CI shell;
  right-hand sides of `=`/`!=` stay quoted so they cannot turn into globs.
- **Explicit function returns** (`return $?` where the last status matters),
  **`*) ;;` default arms** on every `case`, **positional parameters read into
  named locals**, and **literals repeated three or more times hoisted** into
  file-level constants. No gettext msgids changed.
- **Helper extractions** keep every function at radon/`shell_complexity` rank A
  (CCN ≤ 5), and **file splits** keep everything under the 600-line cap:
  `lib/install-components-uinput.sh`, `scripts/docker-utils-parallel.sh`,
  `scripts/coverage/kcov-display-scenarios.sh`, and
  `tests/unit/shell/test_pipeline_ci_parity_sonar.py`.
- **Arithmetic safety**: every `[[ -eq/-lt/… ]]` operand that comes from the
  environment, files, sysfs or command output is digits-checked first, so a
  value like `a[$(cmd)]` can never be evaluated.

### 🐛 Fixes found during hardware validation

- **Zero-padded numbers read as decimal again.** Inside `[[ ]]` bash reads a
  leading `0` as octal (`08` errors, `0150` becomes 104). The new
  `_asus_decimal` helper strips leading zeros before comparisons in
  `INSTALL_COMMAND_TIMEOUT` / `INSTALL_COMMAND_TIMEOUT_MAX` clamping and the
  test-mode root check, and `_normalize_fan_value` does the same for the fan
  profile. Plain parameter expansion is used instead of `$((10#x))`, which
  SonarQube's shell parser rejects, silently skipping the file.
- **Esc / Cancel in the installer checklist aborts the install.** The ncurses
  component TUI returned "cancelled", but `_prompt_tui_selection` read `$?`
  after an `if …; fi` (always 0), so the installer fell back to the text prompt
  instead. It now prints `Installation cancelled by user.` and exits 1.
- **Real-system E2E runs again.** `tests/e2e/real/` is now a package, so
  `scripts/run_real_e2e.sh` can discover its tests (it previously stopped with
  "Start directory is not importable").
- **Esc really cancels the Display Toggle OSD.** The hotkey daemon killed
  `asus-display-mode.sh --cancel-osd` after 0.5 s while its four injection
  round-trips took up to 0.8 s, so Super could stay latched (the next key then
  switched the monitor layout) and a stale `.cancel` marker stopped later OSD
  sessions from releasing. The dismiss is now a single ordered injection
  (ydotool `-d 2`; xdotool without `--clearmodifiers`, which released Super
  before Escape), a stale `.cancel` expires after 3 s, and the daemon gives the
  cancel its full 1.0 s budget.
- **SonarQube now analyses every product script.** `bin/asus-sound-fix.sh` and
  `bin/asus-screenpad-brightness.sh` used `$((10#x))`, which Sonar's shell
  parser rejects, so they were silently skipped; they now use the same
  leading-zero strip and received the same shell cleanup.
- **No more intermittent uninstall "completed with errors" in containers.**
  `printf … | grep -q` under `pipefail` could SIGPIPE on an early match, so a
  recognised systemctl transport error counted as a failure; pattern checks in
  `uninstall.sh`, `lib/asus-session.sh`, `lib/asus-display-mutter.sh` and
  `lib/asus-display-osd.sh` now use here-strings. `scripts/run_real_e2e.sh` no
  longer leaves root-owned bytecode in the checkout.
- **kcov coverage held at ≥90%** on `lib/asus-common.sh` and
  `lib/install-mate.sh` by exercising notification-id and MATE write-failure
  paths directly in the driver shell.

### ✅ Hardware validation (UX582HS, Ubuntu 26.04, GNOME Wayland)

camera privacy toggle, ScreenPad on/off with brightness restore (including the

## 📦 Installation Quick-Start

### Ubuntu PPA (resolute)

```bash
sudo add-apt-repository ppa:ventura8/asus-zenbook-linux-tools &&
  sudo apt update &&
  sudo apt install asus-zenbook-linux-tools
```

### GitHub Release packages (all supported families)

Download assets and **`SHA256SUMS`** from the
[v1.0.9 GitHub Release](https://github.com/ventura8/asus-zenbook-linux-tools/releases/tag/v1.0.9).
Verify the downloaded asset before installation:

```bash
grep -F 'your-asset-filename' SHA256SUMS | sha256sum -c -
```

| Asset | Install (after checksum verify) |
| --- | --- |
| `.deb` | `sudo apt install ./asus-zenbook-linux-tools_*.deb` |
| `.rpm` (Fedora/Rocky/Alma) | `sudo dnf install ./asus-zenbook-linux-tools-*.rpm` |
| `.rpm` (openSUSE) | `sudo zypper install --allow-unsigned-rpm ./asus-zenbook-linux-tools-*.rpm` |
| `.pkg.tar.zst` | `sudo pacman -U ./asus-zenbook-linux-tools-*.pkg.tar.zst` |
| `.AppImage` | `sudo ./asus-zenbook-linux-tools-*-x86_64.AppImage` |
| `.flatpak` | `sudo flatpak install --system ./asus-zenbook-linux-tools-*.flatpak` then |
| | `sudo flatpak run org.github.ventura8.AsusZenBookLinuxTools` |
| `.snap` | `sudo snap install --dangerous ./asus-zenbook-linux-tools_*.snap` (after checksum verify) |

Reconfigure after any native package install: `sudo asus-zenbook-configure`.

### Download install.sh, verify checksum, and run with sudo bash (any supported distro)

```bash
curl -fsSL \
  https://raw.githubusercontent.com/ventura8/asus-zenbook-linux-tools/v1.0.9/install.sh.sha256 \
  -o install.sh.sha256 &&
  curl -fsSL \
  https://raw.githubusercontent.com/ventura8/asus-zenbook-linux-tools/v1.0.9/install.sh \
  -o install.sh &&
  sha256sum -c install.sh.sha256 &&
  sudo bash ./install.sh
```

Both files come from the same GitHub release tag; `sha256sum -c` is an integrity
check that the downloaded script matches its checksum file—not independent or
authenticated verification from a separate trusted channel.
